# osd — interface

`osd` offers one entry per operation on a descriptor: read, write, resolve, convert. Every operation returns its result or a typed fault; none performs I/O. The exports below exist: `read`, `write`, `resolve`, `convert` and the types of 0.4, 0.5 and 0.6. Once the framework's Rust tooling exists, the list between the generated markers is drawn from the crate's rustdoc comments.

## The faults

A fault's `kind` is one of:

- `Syntax` — the text is not JSON.
- `UnknownField` — a field the version does not define, or, in a `midi_of` file, a key that is its target's.
- `BadValue` — a value outside its type or its closed list, or a link that names no catalogue id, another maker's file or another device.
- `Missing` — a required field is absent.
- `UnreadVersion` — at `/$schema`, an address of a known host whose version the crate does not read (the fault names the address and the versions read), or whose version is read but whose address is not one of that version's identifiers (the fault names the address and the one accepted).
- `LinkMissing` — a shared-MIDI or profile link names no file, or a profile without the block named.
- `LinkCycle` — the links form a cycle.
- `LinkTooDeep` — the links go deeper than 8.
- `NotConvertible` — a field the target version cannot hold.

## The `$schema` identifiers

One table, read by `read` and written by `write`. `<kind>` is `device`, `profile`, `sound`, `fingerprint` or `firmware`; any other address of a known host is refused.

| Version | Accepted `$schema` |
|---|---|
| 0.4 | `https://synthhub.roomi-fields.com/osd/0.4/<kind>.schema.json` |
| 0.5 | `https://w3id.org/osd/0.5/<kind>.schema.json` |
| 0.6 | `https://w3id.org/osd/0.6/<kind>.schema.json` |

0.6 is read as 0.5 is, except that a repeated `capabilities` entry is `BadValue` at `/capabilities`, and that a firmware names `targets`, each with its `midi`, in place of `device`, `based_on` and `midi`.

## The guard

- The conformance cases of every version it reads, run by `cargo test -p osd`.
- The SyntHub catalogue, when `SYNTHHUB_DEVICES` names it: every driver and profile read, written back unchanged, resolved, and valid against the schemas once written (`cargo test -p osd`); read and resolved within docs/CADRE.md R16 (`cargo bench -p osd`); resolved as osc-bridge resolves it (`tools/osc-bridge-parity`, beside an osc-bridge checkout).
- The schema its types describe, compared with the published schema of the newest version.
- `cargo-semver-checks` on each release, once the crate is published.
- The lines of `osd-formats` and `osd-cli` in « ## Consumers », compared with every `.rs` file under their `src` by a day test (`cargo test -p osd`, `tests/it/consumers_line.rs`): a name read from `osd` (`osd::X`, `use osd::{…}`) that the line does not list, a name the line lists that is no longer read, and a writing that hides the names read (a glob at the root of the crate, a renaming of the crate) are refused by name. The lines of the consumers outside this repository are not checked.
