# Changelog

## Unreleased

- The page of each importable format (`docs/<format>.md`, « Round trip on public files ») publishes the round-trip figures on public files of the partner: the values carried, lost and structure by kind, with each file's address at a pinned revision, SHA-256, licence and credit. The files are not in the repository: a test replays the count on the folder `OSD_PARTNER_FILES` names. The MIDI 2.0 page says no public file was found; the Deluge and KnobKraft pages say there is no round trip.

- Converters now name in the losses what they lost silently: `midi-csv` import, a row left with no way, at its line; `midnam` import, a `Patch@Number` that is not a whole number, a `ProgramChange` that is no program change number, and the `Name` of a set or list of names the export writes otherwise; `electra-one` import, `offValue` and `onValue` of a pad whose range is the whole scale; `electra-one` export, a command whose parameter number a source keeps; `oscquery` import, a type tag the export writes as another.

- `electra-one` import: a checksum without `length` is no longer read as covering every byte before it. The page of the maker gives it the default 0, which OSD cannot write: no command is written, and a loss at the message names the checksum without length and the default 0.

- `midi-csv` and `electra-one` exports: the losses come in the order of the descriptor given, whether the writer, the comparison with the import or the lost order of an element names them.

- `midi-csv` and `electra-one` exports: the export imports the file it writes and names in the losses every field of the device given that comes back missing, changed or added, at its JSON pointer or at a block that holds it, each control, command and way beside the one it became. Newly named, among others: `osc` and `osc_prefix` when the import builds another, a `title` written from the address or the role, `values`, `role`, `priority`, `step_count`, `readings`, `scale`, `expects`, a `range`, a `transmit` or a `recognize` that is not given back, `value_bits` (a 7-bit NRPN or RPN way of a preset comes back on 14 bits), a name, a section or a label the preset cuts or renames, a control a preset gives back in another order, the blocks `contexts`, `sound_transfers` and `resources`, each `_` note, and `device.name` and `device.vendor` of a CSV with no row an import takes.
- `electra-one` import: every key of a preset, at any depth, that the import does not read is in the losses at its pointer or at a block that holds it, among them `deviceId`, the `id` of a control and of a value, the name of a group no control or command written is in, and each attribute of a device (in place of one loss at `/devices`).

- `electra-one` import: the range of a way and of the argument of a command is the MIDI range of the message (`min` and `max`, else those of the value; on a pad `offValue` and `onValue`); a range equal to the whole scale with no bound on the value gives none, and a bound that differs from the range carried is a loss at its pointer.

- `electra-one` import: a `cc7`, `cc14`, `nrpn` or `rpn` message with `relative: true` is a way with `transmit` and `recognize` `relative`. A SysEx message whose `data` is a number takes the template of that id in the `messages` of the device its `deviceId` names, and gives the command the same template written inline gives. A template whose `direction` is `in` is never sent: no command, and a loss at the message.

- `electra-one` export: each message has the `min` and `max` of the scale of its way or argument (a pad also `offValue` and `onValue`, `onValue` 127 for a command without argument), and the value has bounds only when the descriptor gives a range (a list of named values no longer takes its first and last value). A relative way is written as `relcc` for a CC of one number, else with `relative: true`. A command whose frame holds fixed bytes between F0 and F7, the argument `value` (u7, or u14 as `u14_lsb` and `u14_msb`) and checksums is written as a SysEx template, a fader when it has an argument; any other frame is a loss at `/commands/N/frame` with each field of its argument. A frame that does not start with F0 and end with F7 is no longer written.

- `midi-csv` export: the width of a 7-bit NRPN way written on a row is named as a loss at `/cc_params/entries/N/ways/M/value_bits` (the CSV has no column for it and the import reads every NRPN on 14 bits; without bounds on the row, its scale becomes 0 to 16383). The default of such a way without a range, written in `nrpn_default_value` on a row without a CC, is also named at `/cc_params/entries/N/default`: it is read on 0 to 16383, not 0 to 127. The columns are unchanged.

- `electra-one`: the import gives the `min` and `max` of a SysEx value to the `range` of the `value` argument of its command (a lone bound is a loss, a bound that is not a whole number is refused), and names at `/controls/N/values/M/min` and `/max` each bound of a value with a message that nothing written takes (no argument, a lost kind or template, a claimed message); these bounds were dropped

- `electra-one`: the import names in the losses each key of an overlay a control reads other than `id` and `items` (`/overlays/K/<key>`), and each key of an item a control holds other than `value` and `label` (`/overlays/K/items/I/<key>`), once each; these keys (a `color`, for instance) were dropped without a word.

- `midi-csv` export: for a control with a CC and an NRPN of which one way alone has a range, when the message of the other implies another scale (0 to 127 or 0 to 16383), the bounds columns hold that range and the implied scale: imported back, each way keeps its scale. Until now the one range of the row went to both ways, with no loss named. A default on the reference scale is written in the column of the way that gives it, which the import puts first; the lost order of the ways is named when it changes.

- `electra-one`: the import writes no control whose message an earlier control it writes already claims, as the 0.7 reader judges it (a 14-bit CC claims its two numbers, a relative CC its number, an NRPN and an RPN of one number stay two messages; no channel is written): the loss is at `/controls/N/values/M/message`, and an overlay no control written reads is named. The `values` of a control (now of a relative CC too, whose overlay was a loss) are the items of its overlay, in order, that have a text label and a whole value inside the scale of its way, two items of one label included; every other item is a loss at `/overlays/K/items/I` naming the control. Until now the import could return a descriptor the reader refused, and kept one value per label, sorted by label.

- `electra-one`, `midi-csv` and `midi-triggers-csv` read their result back with `osd` before returning it, by `import` and `import_into`: a result the reader refuses is `InvalidFile` at the empty place, with the reader's rule and pointer. `import_into` reads back a base of 0.7 before it adds the file: one the reader refuses is `NotConvertible`, at the pointer `osd` gives, its rule saying the base does not read in 0.7.

- `midi-csv` export: for a control with an NRPN and a 7-bit CC, neither with a range, whose default of 127 or less is on the scale of the NRPN, the bounds columns hold the range each way implies (CC 0 to 127, NRPN 0 to 16383) and the default is in `nrpn_default_value`: imported back, the NRPN is first and the default keeps its scale. Until now the default came back on the CC, 0 to 127, with no loss named for it. In the order CC then NRPN, the lost order is named.

- `import`, for every format that imports, and `import_into` refuse a source the 0.7 reader of `osd` refuses in the descriptor they would write (a `type` named after a product, such as `pencilresearch`, or outside the list without the form of an extension, a `license` or a `provider` that is not well formed, an empty `id`, and for `import_into` an `id` a source of the base already has): the new `FaultKind::SourceRefused` (**breaking** for an exhaustive `match`), at `source/<field>`, with the reader's rule; no descriptor is returned. Until now the source came out as given, in a descriptor the reader refused.

- `midi-csv`: a row whose `cc_lsb` equals its `cc_msb` gives a CC way of that one number, without `value_bits`, and a loss at `cc_lsb` (a 14-bit pair takes two distinct numbers); it gave a way the reader refused.

- `midi-csv`: a default outside the scale of its control on a row without a range (0 to 127 for a CC of one number, 0 to 16383 for a 14-bit pair or an NRPN) is no longer written, and is a loss at its column. On a row with a CC and an NRPN and no range, an `nrpn_default_value` above 127, taken alone, makes the NRPN the first way; the export writes it back in `nrpn_default_value`.

- The pointer of the `NotConvertible` fault of `import_into` names a place of the base given (for example `/_midi_of_sources`), as the converter of `osd` gives it, and its message says that the base does not convert to 0.7: it no longer speaks of a key of the version reached.

- The export of a device of 0.4, 0.5 or 0.6 writes no number its source does not give for a message not fully known (an NRPN or an RPN given by one number, a `cc_lsb` without its `cc`): `osd` gives it no way, so the file holds the other messages of the control alone. The `midi-csv`, `electra-one`, `midnam`, `oscquery`, `midi2-controllers` and `deluge` exports name it as a loss at its field (`/cc_params/entries/N/nrpn_msb`, `…/cc_lsb`, `…/also/0/rpn_lsb`), as they name an `nrpn_lsb_range` no way takes. Until now the number came out beside a 0 the source did not give, and a `cc_lsb` alone came out as the CC of that number.

- The date a base before 0.7 already holds in a source (`imported_at`) is kept as `_imported_at` in the descriptor `import_into` returns (`_imported_at_2`, then the next number, when that key is taken), as the converter chain of `osd` writes it.

- The `imported_at` of the source given to an import is kept by every format that imports (`midi-csv`, `midi-triggers-csv`, `electra-one`, `midnam`, `oscquery`, `midi2-controllers`), through `import`, and through `import_into` for the two CSVs: 0.7 has no field for it, so its value is written unchanged as the note `_imported_at` of the source added (`_imported_at_2`, then the next number, when that key is taken), as the converter chain of `osd` writes it, and is no longer a loss; the other keys of the source are kept.

- Each format is one module of its own behind one contract (name, media type, extension, import, export, import into a base), and the list of formats holds one line per module, so that a converter is changed or added by one pull request (`CONTRIBUTING.md`, « Add a converter »). `Format::imports_into` says whether a file of the format can be added to a descriptor. The refusal of `import_into` for the other formats is still `InvalidFile` at `format`, with a new rule text: it names the format refused and each format that can (`midnam cannot be added to a descriptor: only these formats can: midi-csv, midi-triggers-csv`).

- A control with no message (an entry with no way) of a base before 0.7 no longer makes `import_into` fail: it is kept with `ways: []`. The pencilresearch/midi CSV export writes the row of such a control with no CC nor NRPN and names in the losses the control at its pointer (an import drops the row) and each of its `scale`, `range`, `transmit`, `recognize`, `nrpn_lsb_range`. The OSCQuery export writes the node of such an entry (`cc_params` or `params`) with the entry's `range` as its `RANGE` and names in the losses each of its `scale`, `transmit`, `recognize`, `nrpn_lsb_range`.

- `import_into` converts a base before 0.7 to 0.7 by the converter chain of `osd` (`convert_to`) before it adds the file, so that the descriptor reads in 0.7 whatever the age of the base: every block of the base comes out as the chain gives it, and what the chain removes is not a loss of the file. A base the chain or the reader refuses is the new fault `NotConvertible`, at the pointer `osd` gives.

- 0.7 (candidate): the `provider` of a source (proposal 0010). An import writes the one the caller gives and guesses none from the format. `credit_to_carry` and the credit text of the Deluge, KnobKraft, MIDNAM and OSCQuery exports name a source's `provider` after its type.

- The imports write a 0.7 descriptor, whose credit is `sources`; the exports name the credit at `/sources` in their losses and in `NoSources` (a descriptor read from a text before 0.7 is the same device). `credit_to_carry` lists the sources when `lost` names `/sources`; the KnobKraft licence warnings are losses at `/sources/N/license`.

- The partners' converters write and read the fields of 0.7 instead of the `_` keys: the midi.guide CSV of the controls reads `title`, `description`, `value_description` and `notes` (columns `parameter_name`, `parameter_description`, `usage`, `notes`), the CSV of the triggers `description`, Electra One and MIDNAM `title` (a control's name; a command's for Electra One). An import writes a `title` only when the source gives a non-empty name, never the address, and no empty `title`; an export without a `title` keeps the fallback by the address it declared. An export names in the losses a `description`, `value_description` or `notes` the preset or the DTD has no place for. `_name`, `_usage`, `_description` and `_notes` are no longer read: a 0.6 descriptor goes through the converter of `osd` first (proposal 0007).

## 0.6.0 - 2026-11-23

- The NRPN and RPN values say their width (0.6 `value_bits`): the MIDI 2.0 controllers import writes `7` for a `numSigBits` of 7 and `14` for any other width, and reads `value_bits` back for `numSigBits`; the Electra One preset, the pencilresearch/midi CSV and MIDNAM, which do not say the width, write `14` on every NRPN and RPN.

- The MIDI 2.0 controllers import reads the nine types of the norm (`cc`, `chPress`, `pPress`, `nrpn`, `rpn`, `pBend`, `pnrc`, `pnac`, `pnp`) and no longer makes a `params` block from a `param` type, which the list does not carry (a block of `osd` asks three SysEx fields that a controller list does not say); a type of the norm that the descriptor has no field for (`chPress`, `pPress`, `pBend`, `pnrc`, `pnac`, `pnp`) is a loss, and the entry is not carried. Any other value of `ctrlType` is refused.

- The Electra One import converts a SysEx template instead of losing every computed byte. A checksum element of the preset (`roland`, `waldorf`, `fractal`; `start` as a number or text; `length` optional) becomes OSD's checksum (`twos7`, `sum7`, `xor7`, with `from` and `length`); an unknown algorithm or a missing start is a loss at `/controls/N/values/M/message`, and no half-written command is kept. A value byte (7 bits, or two bytes msb/lsb) becomes a command argument (`u7`, `u14_msb`, `u14_lsb`). A parameter byte, a Lua function (named, never read nor run) and any other element without an OSD form are losses naming the control. The source keeps `revision` (passed by the caller in `Source`), `sha256` (of the preset text received, computed by the import) and `parameter_numbers`. `docs/electra-one.md` lists, per behaviour of the former SyntHub importer, whether it is kept (with its case) or lost. Reason: a preset shared for one controller keeps the messages that make the device answer; Electra One drivers already published by SyntHub may change on a new import, where a byte built at send time has no OSD form.

- The MIDI 2.0 Property Exchange controllers export and import say the norm's numbers (M2-117-UM v1.0, with the scaling of M2-115-U v1.0.2). `channel` is written from 1 and read back to OSD's 0 to 15; the import refuses a channel above 16 with a reason that names its Group (17-32 is Group 2), and a channel of 0 or below. `default` and `minMax` are written as unsigned 32-bit values scaled from the control's raw values with `numSigBits` (Min-Center-Max for Control Change, NRPN and RPN of LSB 32 to 127; Zero-Extension for RPN of LSB 0 to 31), and the import scales them back (`numSigBits` absent is 32). A negative bound of `range` or a negative `default` is named as a loss and not written, the norm's values being unsigned. `docs/midi2-controllers.md` and `docs/controls.md` say it with the norm's words. Reason: a controller list written from an OSD descriptor is one a MIDI 2.0 device reads right.

- The pencilresearch/midi CSV export names, at `/cc_params/entries/N`, the loss of the order of a control's ways when the first way is an NRPN and the second a CC: the CSV does not say the order, and the import puts the CC first. The loss is not named when the NRPN default column carries the order (an NRPN first way of a different range, with a default), nor when the CC is first. `docs/midi-csv.md` says what the CSV carries of the order. Reason: a partner who goes through the CSV and back knows what the round trip loses.

- The OSCQuery export keeps a command whose address has captures: each capture stays `{name}` in its segment (`/track/{n}/volume` is a method under the containers `track` and `{n}`), with its arguments, bounds and parents; the loss « the address has a capture » no longer exists. A command whose address a node already holds, or with a method on its path, is still named in the losses at `/commands/N`. The import reads a segment, or a part of one, of the form `{name}` as a capture (the command's address is an array of text and capture segments), so OSCQuery, OSD, OSCQuery keeps these commands; a segment with braces that is no capture (`{a,b}`, `{1x}`, two captures side by side) is not imported and the losses name its place. Reason: the service's export and the descriptor 0.4 already wrote `{n}` in the path, and an agent drives « track 3 » through it.

- The pencilresearch/midi CSV places a control's default in the column of its first way: an NRPN first way whose range differs from the CC's exports it in `nrpn_default_value`, and the import makes the NRPN the first way of a row whose only default is in that column with ranges that differ, so the round trip keeps the value. With equal ranges, or a CC first, nothing changes. A default on a control whose first way is an RPN, with a CC or NRPN further on, is a loss at `/cc_params/entries/N/default`, written in no column.

- Each format says the media type and the extension of the file it writes: `Format::media_type` and `Format::extension` (extension without a dot), following the table of `docs/INTERFACE.md`, so osc-bridge and SyntHub write no case per format when they place an export or offer it for download. Types are IANA's where one exists (`application/json`, `application/xml`, `text/csv`). Departures, each with its reason in INTERFACE.md: `text/x-python` for KnobKraft (IANA registers none for Python; the usual type, that of Python's `mimetypes`), `application/xml` for MIDNAM (the MIDI Association declares no type), and `epr` for Electra One (the extension the maker's repository gives its presets; the maker's documentation names none).

- The KnobKraft skeleton states its own licence, `# SPDX-License-Identifier: AGPL-3.0-only`, before the credit of the sources. Each source whose licence is not allowed under the AGPL-3.0, or not recognised (none included), gets a warning line under its `# Source:` line and a loss at `/_sources/N/license`; the export never refuses for it. `docs/knobkraft.md` gives the piece of the licence and a line per allowed licence.

- `Format::Knobkraft` writes a device with sound transfers as a skeleton of a KnobKraft Orm adaptation (Python text, by Christof Ruch, AGPL-3.0): the credit of the sources, then `name`, `numberOfBanks`, `numberOfPatchesPerBank` and `createEditBufferRequest` with the constants the descriptor gives. Each other function of the adaptation interface, and each of these when the descriptor does not give its constant, is named as a loss with its reason. A descriptor without `_sources` is refused (`NoSources`), one without `sound_transfers` too (`NoSoundTransfers`, new `FaultKind`). An adaptation is never read nor run: `import` returns an `InvalidFile` fault. `docs/knobkraft.md` cites each function with its section of the programming guide and the revision of KnobKraft Orm.

- `Format::Deluge` writes a resolved descriptor as the device definition the Deluge firmware reads (`midiDevice` with `ccLabels`, one attribute per CC 0 to 119), so a shared descriptor names its commands on a Deluge as it is. The name of a command is the one the MIDI 2.0 export derives (role, else a section starting with `/`, else the OSC address), escaped for XML and written whole, since the Deluge does not cut it. The CCs come in ascending order; a second command on a CC, a command without a CC or above 119, and each field the format does not carry (range, named values, channel, `/_sources`) are named as losses at their JSON address. The sources' credit and licence go in an XML comment, with `--` broken so the document stays well formed. A descriptor without `_sources` is refused (`NoSources`). The Deluge is not imported: `import` returns an `InvalidFile` fault.

- The pencilresearch/midi CSV imports a row with a CC and an NRPN as one control (0.6): the CC is the first way, the NRPN the first of `also`, and the row's single range goes to each way; the control has one default, the CC's. The export writes one row per control, from its first CC way and its first NRPN way, the range the two ways share written once in the CC columns, so the round trip CSV, OSD, CSV of such a row loses nothing. A way a row cannot carry (a second CC or NRPN, an RPN) is a loss at its pointer `/cc_params/entries/N/also/M`; the round trip OSD, CSV, OSD is not promised for it. A way whose message an earlier row (or the base of `import_into`) already claims is left out and named as a loss at its cell, and a row left with no way is lost, so the imported descriptor reads in 0.6. The Electra One export names `also` as a loss: a preset binds one message to a control.
